---
title: Uploads & Streaming
description: How files flow into each driver, including streaming, multipart uploads, cancellation, and progress
---

All drivers accept a WHATWG `ReadableStream<Uint8Array>`:

```ts
const stream = new ReadableStream({
  start(controller) {
    controller.enqueue(new TextEncoder().encode("file content"));
    controller.close();
  },
});

const result = await client.upload(stream, {
  filename: "report.pdf",
  path: "invoices/2024",
  mimeType: "application/pdf",
});
```

## Streaming behavior per driver

| Driver | Behavior |
|--------|----------|
| `LocalDriver` | **True streaming.** The web stream is piped to disk via Node.js streams with backpressure. Memory usage stays constant regardless of file size. Enforces `maxSizeBytes` while streaming. |
| `S3Driver` | **Streams with bounded memory, always.** With `options.size` (≤ 5 GiB) the payload is sent as a SigV4 `aws-chunked` body whose chunks are signed lazily as they are read (backpressure preserved, zero buffering). Without a known size, or beyond 5 GiB, the driver falls back to a multipart upload, reading the stream into part-sized buffers (default 8 MiB, minimum 5 MiB), so peak memory stays bounded. |
| `CloudinaryDriver` | **Streams with bounded memory.** Files up to `chunkSize` (default 20 MiB) go up in one request; larger ones use Cloudinary's chunked upload, holding about one chunk in memory at a time. Enforces `maxSizeBytes` while streaming. |

When the size is known, pass it to unlock the leanest (single-request) streaming path:

```ts
const result = await client.upload(stream, {
  filename: "report.pdf",
  path: "invoices/2024",
  mimeType: "application/pdf",
  size: bytes,
});
```

Without `size`, `S3Driver` still streams with bounded memory via a multipart upload. If the stream ends before or after the declared size, the upload is aborted and fails with a validation error instead of silently storing a corrupted object.

## Multipart uploads

`S3Driver` splits large objects into parts via the S3 multipart flow (`CreateMultipartUpload` → `UploadPart` → `CompleteMultipartUpload`) in three situations:

- the size is unknown: the stream is read into part-sized buffers instead of being buffered whole;
- the object exceeds 5 GiB, the single-`PUT` cap;
- `forceMultipart: true` is set.

Multipart parts are uploaded sequentially as the stream fills each buffer, so peak memory is bounded by `partSize` (default 8 MiB, minimum 5 MiB) regardless of object size. If the stream mismatches a declared `size`, the driver aborts the in-flight multipart upload and throws a validation error.

`CloudinaryDriver` uploads files larger than `chunkSize` in chunks (`X-Unique-Upload-Id` + `Content-Range`), so very large files never sit in memory whole. `LocalDriver` has no concept of parts because it streams straight to disk.

## Cancelling uploads

Pass an `AbortSignal` in `UploadOptions` to cancel an in-flight upload. On abort, every driver rejects with a `DOMException` named `AbortError` (detectable via `err.name === "AbortError"` or `abortError()` from `@fileway/core`):

```ts
const controller = new AbortController();

const upload = client.upload(stream, {
  filename: "large.bin",
  signal: controller.signal,
});

controller.abort();

try {
  await upload;
} catch (err) {
  if (err.name === "AbortError") {
    // cancelled cleanly
  }
}
```

| Driver | Behavior on abort |
|--------|-------------------|
| `LocalDriver` | Destroys the source and destination streams and unlinks the partial file, so nothing is left on disk. |
| `S3Driver` | Cancels the request and source stream. For multipart uploads it first sends `AbortMultipartUpload` so no orphaned parts remain in the bucket. |
| `CloudinaryDriver` | Aborts the upload request. |

## Tracking upload progress

Pass `onProgress` in `UploadOptions` to receive `{ bytes, total?, progress? }` as chunks flow through the stream. `total` and `progress` (0..1) are present only when `options.size` is known; otherwise only cumulative `bytes` are reported.

```ts
const result = await client.upload(stream, {
  filename: "large.bin",
  size: totalBytes,
  onProgress: ({ bytes, progress }) => {
    updateProgressBar(progress ?? bytes / totalBytes);
  },
});
```

Event cadence is adaptive: a significant chunk (≥ 256 KiB, or ≥ 5% of a known total) reports immediately, while small chunks on fast streams are coalesced to at most one event per 100 ms. An exact final event always fires (`bytes === total`, `progress === 1`), and no event fires on abort. Progress is measured at the client layer as bytes leave the source stream: Local reports as bytes hit disk, S3 as bytes are streamed or buffered into parts, and Cloudinary as bytes are read into each chunk.

## Retrying uploads

A `ReadableStream` is consumed after one read, so to retry an upload Fileway needs a way to **re-produce** the payload per attempt. Pass `streamFactory` (a function returning a fresh stream) to enable retry. The source must be re-readable (a file path, in-memory bytes, or a re-fetchable URL); a one-shot feed cannot be retried.

```ts
const result = await client.upload(createReadStream(file), {
  filename: "photo.jpg",
  size: stat.size,
  streamFactory: () => createReadStream(file), // fresh stream per retry attempt
});
```

Configure backoff with the client's `retry` option (e.g. `maxRetries`, `baseDelayMs`), and set `retry.idleTimeoutMs` so an attempt that hangs is cancelled and retried instead of waiting forever (see [Timing out stuck attempts](/docs/guide/observability#timing-out-stuck-attempts)). Without `streamFactory`, a failed upload throws immediately, with no retry. Retried uploads re-transmit the payload, so they cost `N+1` egresss on `N` failures. See [Retries](/docs/guide/observability#retries) for the full configuration and which failures are retried.

## Safe retries and upload status

A network failure is ambiguous: the provider may have stored the file even though its response never reached you (a reset connection, a timeout, a proxy that dropped the reply). Fileway handles this with a **stable upload ID**:

- Every `upload()` call gets one `id` (generated, or yours via `options.id`), and every retry of that call reuses it, so the stored name never changes between attempts.
- The client also stamps a per-call token on the object (S3 object metadata, Cloudinary context).
- When an attempt fails with a retryable error, the client first asks the driver whether that object already landed. If it did, with this call's token and the expected size, the upload **succeeds without re-sending anything**. This works even without `streamFactory`.
- Only if the object is not there does the client retry (with `streamFactory`) or throw.

Pass your own `id` to make an upload idempotent across processes, for example a job that may run twice:

```ts
const result = await client.upload(stream, {
  filename: "invoice.pdf",
  path: "invoices",
  id: `invoice_${invoice.id}`, // same id on every run: a re-run overwrites, never duplicates
});
```

Reusing an `id` overwrites that object; that is what makes it safe to repeat. IDs are 1 to 128 characters of `A-Z a-z 0-9 _ -`.

### Checking an upload's status

`getUploadStatus(id, { filename, path })` asks the storage provider directly, so it works from any process, even after a crash:

```ts
const status = await client.getUploadStatus(`invoice_${invoice.id}`, {
  filename: "invoice.pdf",
  path: "invoices",
});

switch (status.state) {
  case "complete": // status.object has path, url, size and driver metadata
  case "pending": // started but not finished (S3 multipart, Local partial file)
  case "missing": // never stored
  case "unsupported": // the driver cannot report status
}
```

| Driver | `complete` | `pending` | Notes |
|---|---|---|---|
| `S3Driver` | `HEAD` on the object | Open multipart upload for the key | Token stored as `x-amz-meta-fileway-upload-token` |
| `LocalDriver` | `stat` on the file | A `.partial` file is still being written | Writes to a temp file and renames it into place, so a failed retry never damages a finished file. No token; recovery checks size |
| `CloudinaryDriver` | Admin API resource lookup | Not available | Token stored in context. Public IDs are `<folder>/<id>` (or `<id>` on dynamic-folder accounts) |

> **Future: async producers (planned).** `streamFactory` is currently **sync-only**: it must return the stream directly. An async (Promise-returning) variant is a planned enhancement, which would let you pass sources like `fetch(url).then((r) => r.body)` to re-fetch the payload per attempt without holding it in memory. Until then, on non-Node runtimes use a sync in-memory producer such as `new Blob([bytes]).stream()` in browsers/edge/Workers, or `Deno.open(path).readable` in Deno.
